## 2. Confirmed findings

### F1 — HIGH — Anonymous public lead endpoint exposes full CRM lead data

**Files:**

- `backend/app/routers/leads.py:177` — `@router.post("/public", response_model=LeadOut, ...)`
- `backend/app/routers/leads.py:210` — duplicate `409` detail includes the submitted email and lead id
- `backend/app/routers/leads.py:305` — returns `_load_lead(...)`
- `backend/app/schemas.py:174` — `LeadOut` includes name, email, phone, raw enquiry text, internal notes, score breakdown, recommendations/activities
- `backend/app/schemas.py:322` — `PublicEnquiryOut` already exists but is unused
- `backend/test_public_enquiry.py:60–63` — test currently requires `status == "new"` and `customer_name` in the public response, thereby codifying the exposure

**Evidence:**

- Live `/openapi.json` reports the public endpoint response schema as `#/components/schemas/LeadOut`.
- The endpoint is anonymous (`public_security` is empty in OpenAPI).
- The test suite passes because it asserts the leaky response shape.

**Root cause:** The public route was not switched to the minimal `PublicEnquiryOut` response after the security hardening, and the duplicate error message was not made generic.

**Proposed minimal fix:**

1. Change the public response model to `PublicEnquiryOut`.
2. Return only `{id, status: "received"}` from the public route.
3. Replace the duplicate `409` detail with a generic message containing no email or id.
4. Update `test_public_enquiry.py` to assert the minimal response and assert that PII/internal fields are absent.

**Risk:** Low. No database schema or authentication change. The public client only needs the acknowledgement id.

### F2 — HIGH — Unverified Firebase email can be promoted to a staff role

**Files:**

- `backend/app/services/firebase_auth.py:110` and `:134` — verification returns only `uid`/`email`, discarding `email_verified`
- `backend/app/services/roles.py:54–83` — `resolve_role()` falls back to matching a staff row by email and binds the caller's UID
- `backend/app/services/roles.py:78` — `find_staff(db, None, email)` does not require a verified email
- `backend/app/services/roles.py:81` — binds the UID to the staff row on first sign-in

**Evidence (isolated in-memory reproduction):**

A staff row with `email="victim.staff@example.com"` and no `firebase_uid` was created in a temporary SQLite database. Calling `resolve_role()` with:

```python
{"uid": "attacker_uid_001", "email": "victim.staff@example.com", "email_verified": False}
```

returned `admin` and bound `attacker_uid_001` to the staff row.

**Root cause:** The backend calls the email "verified" but never checks the Firebase `email_verified` claim. Email fallback is still needed for first-time staff binding, so the check must be added specifically to the email fallback.

**Proposed minimal fix:**

1. Preserve `email_verified` in the claims returned by both Firebase verification strategies.
2. In `resolve_role()`, allow the email fallback only when `claims.get("email_verified") is True`.
3. Keep UID-first matching unchanged, so existing staff whose UID is already bound continue to work even if their token email is not verified.
4. Add hermetic tests for:
   - unverified email + unbound staff row → customer, no UID binding;
   - verified email + unbound staff row → staff role, UID binding;
   - UID-bound staff row with unverified email → still staff via UID.

**Production risk:** This is an authentication change, so it requires explicit approval before implementation. The current live database has 3 staff rows and all 3 already have a bound `firebase_uid` (admin, sales_manager, salesperson); UID-first matching means they should not be locked out. No `email_verified` column exists in the database, and none is needed.

**Status:** **BLOCKED pending approval** because it affects authentication.

## 4. Configurations and risks not verified in this pass

These are **NOT VERIFIED** rather than proven defects:

1. **Production CORS allowlist** — `.env` does not set `CORS_ALLOWED_ORIGINS`; localhost and historical deployment origins remain in the default list.
2. **HTTPS/HSTS** — `ENFORCE_HTTPS` and `ENABLE_HSTS` are not set. Local HTTP is expected; production behavior depends on the deployment environment.
3. **Security-event hash salt** — `SECURITY_HASH_SALT` is not set, so the documented known fallback constant applies.
4. **Database connection/startup timeouts** — `backend/app/database.py:26–31` creates the PostgreSQL engine without `connect_timeout`, `pool_timeout`, or `pool_recycle`; `backend/app/main.py:272–283` performs synchronous startup writes. A remote pooler outage could delay startup/requests. This was not reproduced as a database hang in this pass because the stalled audit script had no active TCP connection.
5. **Silent migration failures** — `backend/app/database.py:135` swallows migration exceptions. Schema drift can therefore start the API with missing columns. No current schema failure was observed.
6. **Post-commit side effects** — `backend/app/routers/leads.py` commits the lead before recommendations/activity/audit writes. A later failure can return `500` after the lead is already saved, encouraging duplicate retries. Not reproduced.
7. **Rate limiter** — in-memory and per-process; documented as defence-in-depth, not a distributed limiter.
8. **CORS error-handler substring check** — `backend/app/main.py:207` accepts any origin containing `localhost` or `127.0.0.1` on 500 responses. Low impact, but stricter membership would be cleaner.
9. **Public chat/voice cost abuse** — `/api/chat` and `/api/voice/webrtc` are public by design; no product decision was made to change that.
